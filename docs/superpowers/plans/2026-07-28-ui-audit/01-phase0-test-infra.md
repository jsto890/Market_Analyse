# Phase 0: Test Infrastructure — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Stand up component-render and route/integration test infrastructure for `dashboard/` so that downstream UI-audit fix phases can write `render()`-based tests that actually exercise components, hooks and routes — not just type shapes — closing the gap the audit calls out at `MARKET_ANALYSE_UI_AUDIT.md` §21 ("none of OL-01 … OL-04 would fail CI").
**Architecture:** One `vitest.config.ts` using Vitest 4's `test.projects` to run two projects — `lib` (existing node-environment unit tests, untouched) and `component` (new jsdom + React Testing Library tests) — plus a separate Playwright config/`e2e/` directory for route-level integration tests against a real `next dev` server. A single `test/render.tsx` helper is the one import downstream authors use for every component test.
**Tech Stack:** Vitest 4.1.8, jsdom 26, @testing-library/react 16.3, @testing-library/user-event 14.6, @testing-library/jest-dom 7, @playwright/test 1.60 (pinned to match the existing `playwright` 1.60.0 devDependency), Next.js 14.2.35 App Router, React 18.3, SWR 2.4.

  import { ReactElement, ReactNode } from "react";
  import { render as rtlRender, type RenderOptions } from "@testing-library/react";
  import { SWRConfig } from "swr";
  import TooltipProvider from "@/components/ui/TooltipProvider";

  function Providers({ children }: { children: ReactNode }) {
    return (
      <SWRConfig value={{ provider: () => new Map(), dedupingInterval: 0 }}>
        <TooltipProvider>{children}</TooltipProvider>
      </SWRConfig>
    );
  }

  function render(ui: ReactElement, options?: Omit<RenderOptions, "wrapper">) {
    return rtlRender(ui, { wrapper: Providers, ...options });
  }

  export * from "@testing-library/react";
  export { default as userEvent } from "@testing-library/user-event";
  export { render };
  ```

  import { vi } from "vitest";

  type FetchResponses = Record<string, unknown> | ((url: string) => unknown);

  export function mockFetchJson(responses: FetchResponses) {
    const resolve = typeof responses === "function" ? responses : (url: string) => responses[url];
    vi.stubGlobal(
      "fetch",
      vi.fn(async (input: RequestInfo | URL) => {
        const url = typeof input === "string" ? input : input.toString();
        const body = resolve(url);
        if (body === undefined) {
          return new Response(JSON.stringify({ error: "not mocked", url }), {
            status: 404,
            headers: { "Content-Type": "application/json" },
          });
        }
        return new Response(JSON.stringify(body), {
          status: 200,
          headers: { "Content-Type": "application/json" },
        });
      })
    );
  }
  ```

## Conventions for downstream test authors

**File naming and location.** Co-locate tests next to the code they cover, under a `__tests__/` folder, matching the existing `lib/__tests__` convention:
- Component tests: `components/<area>/__tests__/<Component>.test.tsx`
- Route/page tests (component-level, e.g. mounting `app/odte/strikes/page.tsx` with mocked fetch): `app/<route>/__tests__/page.test.tsx`
- Playwright route/integration tests: `e2e/<feature>.spec.ts` (note the `.spec.ts` suffix, not `.test.ts` — this is what tells Playwright's `testDir: "./e2e"` scope apart from Vitest's `include` globs, which never match `.spec.ts`).
- Test infrastructure's own tests: `test/__tests__/<helper>.test.ts(x)`.

**Every component test starts the same way:**
```tsx
import { render, screen, userEvent } from "@/test/render";
```
Never import `render`/`screen` directly from `@testing-library/react` in a component test — that skips the `TooltipProvider`/`SWRConfig` wrapping and will make any component using a Radix `Tooltip` throw. The only legitimate direct `@testing-library/react` import is inside `@/test/render.tsx` itself.

**Mocking SWR/fetch.** For a component or page that calls `fetch(...)` (directly or via SWR), call `mockFetchJson(...)` from `@/test/fetchMock` *before* `render()`:
```tsx
import { render, screen } from "@/test/render";
import { mockFetchJson } from "@/test/fetchMock";

mockFetchJson({ "/api/argus/options/live/SPY": { symbol: "SPY", spot: 565 } });
render(<LiveLadder symbol="SPY" />);
```
Match on the exact request URL your component calls (including query string) — `mockFetchJson` does exact-string lookup by default; pass a function instead of an object if you need pattern matching. Every `render()` call gets a fresh SWR cache automatically (`@/test/render`'s `SWRConfig` uses `provider: () => new Map()`), so you never need to manually reset SWR's cache between tests — just don't reuse a single `render()` result's data across `it()` blocks.

**localStorage.** Call `resetLocalStorage()` from `@/test/localStorage` at the start of any test whose component reads persisted state (panels, rails, toggles built on `useLocalStorage`), and `seedLocalStorage(key, value)` to set up a pre-existing value. `useLocalStorage` (`lib/useLocalStorage.ts`) reads from storage inside a `useEffect`, so assert post-mount state with `findBy*` (async) on first render, not `getBy*` — the initial render always reflects the hook's `defaultValue` before the effect runs.

**Never import `@/lib/db` in a component test.** `openDb`/`getDb` (`lib/db.ts`) open a real SQLite file on import; there is no in-memory/mock mode wired into the `component` project. If a component or page depends on data that ultimately comes from `lib/db.ts`, mock the boundary above it (the `fetch` call to the Next API route that reads the DB), not the DB layer itself.

**Asserting on tokens/classNames.** This app has no CSS loaded under jsdom (Tailwind classes are just strings; there's no computed-style testing). Assert directly on the class string with `toHaveClass(...)`, using the exact token classes from the component source (e.g. `bg-warn/20`, `text-pos`, `bg-neg/15`) — never assert on rendered colour/computed style. If a component test needs to prove "uses a token, not a raw palette colour" (relevant to audit findings like OL-09), assert the class does **not** match a raw Tailwind palette pattern, e.g. `expect(el.className).not.toMatch(/\b(bg|text)-(blue|green|red|yellow|gray)-\d{3}\b/)`.

**Testing ARIA state (`aria-pressed`, `aria-current`, `aria-expanded`).** Query by role and assert the attribute directly, after a user interaction via `userEvent` (not `fireEvent`, which skips React's event delegation nuances `userEvent` correctly simulates):
```tsx
const user = userEvent.setup();
render(<LiveToggle />);
const toggle = screen.getByRole("button", { name: /live/i });
expect(toggle).toHaveAttribute("aria-pressed", "false");
await user.click(toggle);
expect(toggle).toHaveAttribute("aria-pressed", "true");
```
For `aria-current` (nav links) and `aria-expanded` (disclosure/accordion controls), use the same `toHaveAttribute` pattern — do not assert on visual class state (e.g. a highlighted background) as a proxy for selection/expansion state; assert the ARIA attribute itself, since that is what the audit's accessibility findings (e.g. OL-19) are about.

**Route-level (Playwright) tests.** Use `page.goto(path)` + `expect(res?.status())` for page reachability, and the `request` fixture (`request.get(path)`) for pure API/JSON routes — do not use `page.goto` for API routes, it forces unnecessary HTML/navigation handling. Any Playwright test written against a documented-but-unfixed audit bug must use `test.fail(true, "<reason + which OL-## + what unblocks it>")` as the first line of the test body, per Task 8's pattern, so CI treats it as an expected failure until the underlying fix ships — and so CI *breaks loudly* (unexpected pass) the moment someone fixes the bug without updating the test.
